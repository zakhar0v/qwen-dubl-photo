Вот алгоритм для ИИ-агента по проектированию конвейерного асинхронного хеширования. Основная цель: максимизировать утилизацию процессора (CPU) и дискового ввода-вывода (I/O), скрывая задержки чтения файлов.

### 1. Архитектурные принципы

*   **Разделение ответственности:** Четкое разделение на три слоя: `Consumer` (потребитель файлов), `Worker Pool` (вычислители хешей) и `Storage` (запись в БД).
*   **Неблокирующий I/O:** Чтение файлов и запись в БД должны происходить в отдельном потоке или через асинхронные вызовы, чтобы не блокировать основной поток вычислений.
*   **Буферизация (Pipeline):** Данные не передаются напрямую из файла в хеш-алгоритм. Используется промежуточный буфер (очередь задач).

### 2. Структура Конвейера (Pipeline)

Конвейер состоит из трех основных компонентов, соединенных неблокирующими очередями (Queue/Channel):

#### Компонент А: Генератор задач (File Scanner / Producer)
*   **Задача:** Сканирует файловую систему и создает задачи на обработку.
*   **Логика:**
    1.  Получает список файлов из БД (статус `new` или `exif_checked`).
    2.  Для каждого файла создает объект задачи `HashTask`:
        ```python
        class HashTask:
            file_path: str
            file_id: int
            priority: int  # Например, локальные файлы > удаленные
            status: str
    ```
    3.  Помещает `HashTask` в **Очередь Задач (Task Queue)**.
    4.  *Оптимизация:* Если файлов много, генератор должен работать итеративно, не загружая весь список в память.

#### Компонент Б: Пул Вычислителей (Worker Pool)
*   **Задача:** Асинхронно читает файлы и вычисляет SHA256.
*   **Реализация:**
    *   Использовать пул потоков (`ThreadPoolExecutor`) или асинхронные задачи (`asyncio` с `loop.run_in_executor`).
    *   Количество воркеров равно количеству ядер CPU (или чуть больше, чтобы компенсировать ожидание I/O).
*   **Логика работы воркера:**
    1.  Берет задачу из **Очереди Задач**.
    2.  **Чтение:** Открывает файл в режиме `rb`.
        *   *Критический момент:* Чтение должно быть порционным (chunked), например, по 64KB или 1MB. Это позволяет начинать хеширование сразу, не дожидаясь конца файла.
    3.  **Хеширование:**
        *   Инициализирует объект `hashlib.sha256()`.
        *   В цикле: читает чанк -> обновляет хеш (`hash.update(chunk)`) -> освобождает память на чанк.
        *   *Почему так?* Если читать файл целиком в память, возникнет пик потребления RAM. Порционное чтение поддерживает постоянный низкий уровень потребления памяти.
    4.  **Результат:** После завершения чтения возвращает кортеж `(file_id, sha256_hash)`.

#### Компонент В: Сборщик и Запись (Aggregator / DB Writer)
*   **Задача:** Принимает результаты вычислений и обновляет базу данных.
*   **Логика:**
    1.  Слушает канал результатов от Воркеров.
    2.  Копит результаты в буфер (например, 100-500 записей).
    3.  Как только буфер заполнен или прошел таймаут:
        *   Начинает транзакцию.
        *   Выполняет пакетное обновление (`UPDATE files SET sha256 = ?, status = 'hash_checked' WHERE id IN (...)`).
        *   Фиксирует транзакцию.
    4.  *Важно:* Запись в БД должна быть асинхронной относительно вычислений, чтобы не ждать завершения SQL-операции для продолжения хеширования других файлов.

### 3. Обработка сети и локальных файлов (Учет вашего запроса)

Вы упомянули "чтение по локальной сети". Это критичный фактор.

*   **Приоритизация:**
    *   Локальные файлы (SSD/HDD) имеют высокую пропускную способность и низкую задержку.
    *   Сетевые файлы (SMB/NFS) имеют высокую задержку и низкую пропускную способность.
*   **Алгоритм балансировки:**
    1.  Воркеры должны иметь возможность обрабатывать задачи из разных источников параллельно.
    2.  Если воркер ждет чтения сетевого файла (I/O wait), он должен быть готов взять новую задачу из очереди, как только текущее чтение завершится (независимо от того, что другой воркер уже начал читать другой сетевой файл).
    3.  **Предотвращение блокировки сети:** Не используйте синхронное чтение `open().read()` для сетевых файлов в основном потоке. Используйте буферизированное чтение с таймаутами.

### 4. Управление памятью и ресурсами

1.  **Ограничение параллелизма:**
    *   Установите максимальное количество одновременных открытых файлов (file descriptors). Если открыть слишком много файлов одновременно (особенно сетевых), можно превысить лимит OS.
    *   Рекомендация: `max_workers = CPU_COUNT * 2` (для I/O-bound задач) или `CPU_COUNT` (для CPU-bound). Для смешанных задач начните с `CPU_COUNT + 4`.

2.  **Backpressure (Обратное давление):**
    *   Если Воркеры работают быстрее, чем БД принимает данные, очередь результатов будет расти.
    *   *Решение:* Если размер очереди результатов превышает порог (например, 1000 задач), приостановить Генератор задач или замедлить Воркеры. Это предотвратит Out-of-Memory.

3.  **Обработка ошибок:**
    *   Если чтение файла упало (файл удален, нет прав), задача помечается как `failed`, хеш не вычисляется, статус файла остается `new` или ставится `error`.
    *   Воркер не должен падать целиком. Ошибка обрабатывается внутри задачи.

### 5. Пошаговый алгоритм для ИИ-агента (Псевдокод логики)

```text
1. Инициализировать:
   - TaskQueue (очередь задач на вычисление)
   - ResultQueue (очередь результатов вычислений)
   - DBWriter (асинхронный сервис записи)
   - WorkerPool (пул воркеров)

2. Запустить DBWriter:
   - Бесконечный цикл:
     - Ждать результатов в ResultQueue
     - Копить в batch
     - Если batch полный или таймаут:
       - Выполнить SQL UPDATE batch
       - Очистить batch

3. Запустить WorkerPool (N потоков):
   - Для каждого потока:
     - Бесконечный цикл:
       - Взять task из TaskQueue
       - Если task пустой: пауза
       - Открыть file_path
       - Инициализировать sha256_obj
       - Читать цикл:
         - chunk = read(1MB)
         - Если chunk пуст: break
         - sha256_obj.update(chunk)
       - Закрыть файл
       - Отправить (task.file_id, sha256_obj.hexdigest()) в ResultQueue

4. Запустить FileScanner (Генератор):
   - Получить список файлов из БД (WHERE status IN ('new', 'exif_checked'))
   - Для каждого файла:
     - Создать HashTask
     - Положить в TaskQueue
   - Пометить в БД эти файлы как 'processing' (чтобы не дублировать при повторном запуске)

5. Мониторинг:
   - Если TaskQueue пуста и ResultQueue пуста и все файлы обработаны:
     - Остановить воркеры
     - Остановить scanner
     - Завершить работу
```

### 6. Ключевые рекомендации для ИИ-агента

1.  **Не изобретайте свой цикл чтения:** Используйте готовые библиотеки для асинхронного ввода-вывода (например, `aiofiles` в Python или `io.Reader` в Go), они уже оптимизированы под OS.
2.  **Инкрементальное хеширование:** Обязательно используйте метод `update()` хеш-алгоритма с порциями данных. Это единственный способ поддерживать низкое потребление памяти.
3.  **Атомарность обновлений:** Обновление статуса файла в БД должно происходить *после* успешного вычисления хеша. Если вычисление провалилось, статус не меняется (или меняется на `error`), чтобы при повторном запуске файл был обработан снова.
4.  **Логирование:** Логгируйте прогресс каждые N обработанных файлов или каждые T секунд, чтобы пользователь видел, что процесс идет, а не завис.

Этот подход обеспечит высокую пропускную способность, так как пока один воркер ждет чтения с диска/сети, другой воркер уже вычисляет хеш для уже прочитанного файла, а третий воркер может начать читать следующий файл.
